# AGENT.md

For coding agents. Humans read [README.md](README.md). Security policy: [SECURITY.md](SECURITY.md). Conduct (fail-fast): [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). This file is the `AGENTS.md`-style contract for adding a sensor. Keep it that small.

## Intent

Publish numbers to MQTT so Home Assistant can discover them. Not a framework, not a metrics stack, not a supervisor. Everything here is meant to run as root. If it seems you would not want to be doing what a sensor is doing as root, it probably does not belong in this project.

Because it all runs as root, spare no effort reducing supply-chain risk. Details: `SECURITY.md`. No `requirements.txt`, no pip, no PyPI. Only packages on the distro's standard list. If a sensor's logic depends on something that could be a supply-chain risk, and a small custom solution would be safer, consider that rework. Not necessarily right away — that is the spirit. Stdlib, a sysfs fd, a local log, or a binary already on the host beat a new package. Do not add dependencies. `paho-mqtt` is the exception that already exists and it arrives via the distro (`python3-paho-mqtt`).

## Adding a sensor

1. New script at repo root (host collectors) or under `support/` (shared market/data helpers this project needs). Placement follows where the data comes from: fetched from the internet (network stats, prices) → `support/`; reported directly by a local node or program (Chia netspace from the farmer's own full node) → host collector entity, even when the value is network-wide. Market prices: one HA device per real exchange-traded pair (`XMR/EUR`, `PEARL/USDT`, `USDT/EUR`, identifier `<base>_<quote>_price`), never a synthetic aggregated or cross-converted price; the device has a generic `Price` entity (`<base>_<quote>_price`) plus one entity per source (`<base>_<quote>_<source>_price`, name `<Source> Price`); `Price` is the `avg`/`max`/`min` of the sources per `<BASE>_<QUOTE>_PRICE_MODE` (default `avg`, anything else exits), and adding a source is one fetch function plus a `SOURCES` entry in that pair's own script (`XMR/EUR` predates this and is aligned in a later change). Sources fail fast (one failing fetch exits the collector). A fiat value is a chain of real steps (PEARL→USDT→EUR), each step with its own slippage: new pair collectors read a required `<BASE>_<QUOTE>_SLIPPAGE_PCT` from `.env` and publish it with `mode` as attributes of `Price` every poll; network stats get one device per coin (`Monero`, `Pearl`). Import from `lib` (see Shared code). Do not add packages.
2. `MACHINE_ID = get_machine_id()` and `DEVICE, _ = make_device()` for host collectors (`make_device("windows")` under `windows/`). File: `{source}_{metric}.py`. unique_id and object: `slot_id("{source}_{metric}")` = `{machine_id}_{source}_{metric}` for fixed-name entities. HA `name` is a readable title that includes the metric (`Chia Recompute Server Processing Time`). Never omit the metric. Never use the raw binary name as the HA name. Availability: `sensor/{machine_id}_{source}/availability`. Client id: `{source}-{machine_id}`. Host collectors share one HA device. `support/` scripts may use their own HA device (not `linux_host_<name>`) when the value is not a host metric.

   Identity: the entity id equals the topic id, up to case (exception below). Every discovery payload sets `default_entity_id` = `entity_id(platform, unique_id)` (the builders do it), and topics are `<prefix>/<platform>/<unique_id>/…`. Never use the hostname in a new id: the slot is `MACHINE_ID` as written (Finnish area + machine, e.g. `Olohuone_PC1`; the hostname as-is when unset), and the device is `<kind>_host_<slot>` named `machine_name()` (`Olohuone PC1`: underscores as spaces; the hostname as-is when unset). Keep case wherever HA and MQTT allow it (topics, unique_ids, device names and identifiers; `id_part()` for slugs). The one exception to entity id = topic id: HA entity ids are lowercase only, so `default_entity_id` is `entity_id(platform, unique_id)` = `<platform>.<unique_id lowercased>`; topic and entity id may then differ by case. Always build it with `entity_id()`. Power tracking is by slot, unique hardware names elsewhere. Fixed-name entities (a name in the code: CPU and GPU power and energy, GPU with the index `<machine_id>_gpu0_power`; ids of a specific piece of hardware stay generic, its current model goes in the display name: `GeForce RTX 4080 Power`, `GeForce RTX 4080 (GPU 1) Power` with several GPUs, `<CPU model> Package Power`, XMRig, Chia, sessions, services, APM, reset reason, system battery) are keyed by slot as a prefix, `slot_id(name)` = `<machine_id>_<name>`. Entities discovered from hardware are keyed by that hardware's identity with no slot: an existing unique device identifier as is (peripheral battery `power_supply_<model>_<serial>`, drive `hwmon_drive_temperature_<id>`), GPU health stats by UUID plus a short model for readability (`gpu_stat_id()` = `gpu_<uuid>_<Model>_<metric>`, e.g. `gpu_8b1c…_RTX4080_temperature`; the only id with a model name), and chip-and-channel names that collide across machines get the motherboard prefix `mb_<board>_…` (`dmi_board_id()` / `pick_board_id()`). Otherwise never put a model name in an id; models belong in the HA `name`. Linked devices: hardware that can move between machines (peripheral battery, GPU, drive) is its own HA device from `make_linked_device(identifier, model name, machine device id, …)`, keyed by the hardware (no slot, no hostname), `via_device` = the machine it is in now; its entities are named without the model (`Power`, `Temperature`; HA prefixes the device name). A collector that links devices and has no other entity on the machine device (drives, batteries) also publishes `machine_count()` (diagnostic `<slot>_<metric>` count on the machine device, config before the linked ones), so its `via_device` always exists with a name; HA stub-creates an unknown one, unnamed, shown as the broker address. A linked device another machine could clear (drives) publishes retained `linked_attributes()` (`linked_machine`) on its `attributes` topic: a machine only clears a drive last linked to itself (removal when it leaves), and logs a live claim by another machine as a conflict (one drive cannot be in two machines).
3. One held-open source for the life of the process: sysfs fd, log fd, one subprocess that loops internally (`nvidia-smi --loop=1`, `journalctl -f`), one HTTP/TLS connection, an in-process poll of a runtime dir (`/run/systemd/users`, a unit cgroup), or an inotify fd on the directory of a rarely changing file (`etc_debian_version.py`). **Never** `Popen` per sample. **Never** open a new TCP connection per sample if you can hold one. Reopening a rotated log fd (inode change, once a day) is allowed; do not start `tail`. Do not spawn `loginctl` or `systemctl` to read state.
4. `create_client(..., will_topic=availability)` then `loop_start()`. On connect: subscribe `{prefix}/status`, then discovery JSON + `online`; `create_client` re-runs `on_connect` when HA publishes `online` there, and repeats non-retained `online` on the will topic once, `DISCOVERY_SETTLE_SEC` (2) after every `online` the collector publishes (`_repeat_online`): HA subscribes to an entity's topics only after processing its discovery, so the `online` sent right after discovery is lost. No periodic `online`. Collectors that publish non-retained states slower than that (the `support/` pair and Pearl network collectors) pass `create_client(..., replay_states=True)`, which also replays the last non-retained payload of each non-config topic at that moment. Publishing `offline` to the will topic or `disconnect()` cancels a pending repeat. Do not retain unless there is a clear reason it helps (default: retain is harmful). Each retained publish has a short inline comment with that reason. Never retain discovery or availability (republish on HA `online`, rediscovery and the repeat cover those), except `kmsg_reset_reason.py` which is run-once and has no availability topic. On exit: `offline`, stop, disconnect.
   Rediscovery: `create_client` also watches every config topic the collector publishes non-empty (subscribes to it, `_watch_discovery`). Deleting an entity or device in HA publishes a zero-length payload on its config topics; when one arrives on a watched topic, `on_connect` is re-run `DISCOVERY_SETTLE_SEC` after the last one (one republish per device delete), so the collector's current entities come back with their ids and history and anything it no longer publishes stays deleted. A config topic the collector clears itself (`client.publish(config, "", retain=True)` for hardware that left) is dropped from the watch first. So `on_connect` must publish everything current: every config, `online`, and the state of anything that publishes rarely (or retained / `replay_states=True`). This is the cleanup: removing stale entities is deleting them in HA; collectors have no purge or sweep logic and no CLI. Collectors still clear, at runtime, entities of hardware that leaves while they run (drives, peripheral batteries). HA clears only the config topic; retained states of deleted entities stay on the broker unused (README, Removing entities, clears them with `mosquitto_sub`). There is no purge script.
5. ~1 s using `time.monotonic()` for `dt` (host collectors). `support/` price feeds may poll slower (e.g. 60 s). Drive temperature polls every 60 s (`DRIVE_TEMPERATURE_INTERVAL`) because reads can reset drive spin-down timers.
6. Power: W, `make_power_discovery`, `%.1f`.
7. Energy (if any): RAM only, `energy_wh += power * (dt / 3600.0)`, publish `energy_wh / 1000.0` as kWh `%.6f`, `make_energy_discovery` (`total_increasing`). It resets when the process starts. That is correct for HA. Do not write it to disk.
8. Optional matching `systemd/<script>.service` (all units live in `systemd/`, user units in `systemd/user/`): `ExecStart`, `WorkingDirectory`, `Restart=on-failure`, `RestartSec=10`, `[Install] WantedBy=default.target`. Path stub `/root/mqtt-sensors`. All collectors run as root. Do not add `User=` / `Group=`. Chia paths: `chia_root()` from `mqtt_common` (`pwd.getpwuid(1000).pw_dir / ".chia" / "mainnet"`). Never a username, never `/home/…`, never `Path.home()`.

Other measurement types: `make_sensor_discovery(...)` with the HA unit / device_class / state_class (left out when None) and any other discovery key as a keyword (`json_attributes_topic=`, `suggested_display_precision=`, `entity_category=`); `availability_topic=None` for a run-once sensor without availability. Never hand-build a discovery dict. Do not extend `lib/` for a one-off. Switches use `make_switch_discovery(...)` (same keywords), `switch_mode(env_name)`, and `make_switch_on_message(...)`; numbers use `make_number_discovery(...)` (`number/<object>/{config,state,set}`); services use `service_manager()` → `is_active(name)`, `start(name)`, `stop(name)`, `follow_log(name)` (bare name, e.g. `lightdm`); sessions use `session_source()` → `active_users()`. Power supply batteries are `%` / `battery`. Drive temperatures are `°C` / `temperature`, `%.1f`. Chia plots omit `device_class` (plain count). Chia sizes use `TiB` / `data_size`, netspace `EiB` / `data_size`, ETA `s` / `duration`. Recompute and harvester processing time are `s` / `duration`; publish full precision, set `suggested_display_precision` to 1 on that dict. One sensor per process, except `chia_harvester_processing_time.py` (plot count from the same `debug.log` line), `xmrig_status.py` (hashrate + reject ratio + mining switch + intensity number + profitability factor from XMRig HTTP plus MQTT inputs), `wildrig_status.py` (mining switch plus per-GPU enable switch, intensity number, hashrate, reject ratio and profitability factor from the WildRig Multi API plus MQTT inputs), `interrupts_rate.py` (total, max per CPU, LOC/RES/CAL/TLB/IWI; top device sources as attributes), `psi_stall.py` (cpu/memory/io some, memory/io full), and `collector_cost.py` (total CPU % and voluntary/nonvoluntary context-switch rates; per-collector breakdown as attributes). Publish each sample; do not average. Do not publish fail or gpu flags; gaps in time are enough. Loginctl active users is a string (comma-separated names); no unit, no device_class, no state_class. On/off services are MQTT `binary_sensor` (`device_class=running`, payloads `ON`/`OFF`); config under `binary_sensor/<object>/config`. Controllable on/off is MQTT `switch` under `switch/<object>/{config,state,set}`; XMRig mining is the first (`ON`=resume, `OFF`=pause). XMRig intensity is an MQTT `number` slider 0–100% (`<machine_id>_xmrig_intensity`); thread count is `floor(percent * max_threads / 100)` on the active CPU profile (`max_threads` = `os.cpu_count()`) (`GET /2/backends`, `GET`/`PUT /2/config`); minimum 1 thread (0% sets 1), pausing is the switch; intensity can persist to XMRig `config.json` when autosave is on. LightDM active and Ollama active are switches whose state is `service_manager().is_active("lightdm")` / `("ollama")` (systemd backend: the `<name>.service` cgroup dir existing); `LIGHTDM_SWITCH_MODE` / `OLLAMA_SWITCH_MODE` `read_only` (default) ignores commands and re-publishes state, `control` calls `start`/`stop` (systemd backend: `systemctl start|stop <name>.service`) on a command only (never per sample). XMRig hashrate is `H/s`, reject ratio `%` from `(shares_total - shares_good) / shares_total`. Profitability factor is unitless `revenue/cost` (`hashrate * xmr_per_hs_day / 24 * xmr_eur` over `mining_W/1000 * €/kWh`); `mining_W` is raw `package_W` until ~300 samples (~5 min at 1 Hz) accumulate at full intensity (`threads == max_threads`, not paused; init-only), or `XMRIG_POWER_BASELINE_W` is used as the baseline until then; baseline, hashrate plateau, hints and opt-in contention handling (`XMRIG_CONTENTION_MODE=control`) live in `MiningIntensity` and `Contention` in `lib/xmrig_common.py`, shared by Linux and Windows; then at 100% use `package_W` directly, and when `f < 1` cap with `min(package_W, f * baseline_max_package_W)` (`f = threads/max_threads`); about every 5 min at 100%, if the max `package_W` over the latest ~15 min at 100% (rolling window) differs from baseline by more than ±5%, set baseline to that recent max (no re-init); intensity 0 → `mining_W` 0 (no factor); while paused, last mining hashrate and attributed `mining_W` are kept in RAM so the factor does not collapse. Publish only — no built-in pause/resume from the factor; HA (or later logic) chooses thresholds. Fiat prices are `EUR` / `monetary`; XMR/EUR uses Kraken public ticker last trade. Network block times have three meanings: **nominal** (`<coin>_nominal_block_time`, s; the coin's fixed target: Pearl `targetBlockSecs`, Monero `networkinfo.target`), **difficulty-period** (`<coin>_difficulty_period_block_time`, s; the block time the current difficulty is set for; equals nominal unless a DAA change cap was hit; Pearl and Monero have no such cap, so they are equal), and **current** (`<coin>_current_block_time`, s; a loose recent average, with `window_secs`/`window_blocks` attributes; Pearl is `hashWindowSecs / hashWindowBlocks` from the same stats response, Monero is the time between the tip block and the block 30 heights earlier). Network hashrate is not published; implied current hashrate is `work_per_block / current_block_time` (equivalently target hashrate × nominal / current) and can be derived in HA if needed. Per-H/s-per-day revenue uses reward and difficulty only. Monero network: difficulty (no unit), the three block times, last-block coinbase reward `XMR`, and `XMR/H/s/d` = `reward * 86400 / difficulty`. Pearl network: difficulty (no unit), the three block times, current block reward `PEARL`, and `PEARL/H/s/d` = `reward * 86400 / (difficulty * 2^64 / 65535)` (work per block for Pearl's `0x1b00ffff` difficulty 1; Pearl "hashes" are multiply-accumulates) from pearlchain.live. PEARL/USDT is Gate public spot ticker `last` (no EUR market, no Kraken listing); USDT/EUR is Kraken public ticker last trade. Pair prices and Pearl network states are not retained.

## Hard rules

- No comments.
- Minimal error handling. Assume RAPL, `nvidia-smi`, the Chia farmer on localhost:8559, full node on localhost:8555, farmer + full_node certs and `debug.log` under uid 1000's `.chia/mainnet`, `journalctl -u chia_recompute_server`, `/run/systemd/users`, `/sys/fs/cgroup/system.slice/{lightdm,ollama}.service`, `/sys/class/power_supply/*/capacity` for `type=Battery`, `/sys/class/hwmon/*/temp1_input` for `drivetemp`/`nvme`, `SG_IO` on `/dev/sd*` as root, XMRig HTTP API on `XMRIG_HOST`:`XMRIG_PORT` (default `127.0.0.1:44444`) with `XMRIG_TOKEN` when set, WildRig Multi `GET /` on `WILDRIG_HOST`:`WILDRIG_PORT` (default `127.0.0.1:60061`) while `wildrig-multi.service` runs (refused or dropped connections count as no sample) and `/etc/default/wildrig-multi` with `WILDRIG_GPU_LIST=` and `WILDRIG_INTENSITY=`, Home Assistant `/api/states/<entity>` when `HA_TOKEN` is set, Kraken `api.kraken.com` public ticker, Gate `api.gateio.ws` public spot ticker, the Grok CLI's `auth.json` at `GROK_AUTH_PATH` and `cli-chat-proxy.grok.com`, xmrchain.net `/api/networkinfo` + `/api/block/<height-1>` + `/api/block/<height-1-30>`, pearlchain.live `/api/explorer/stats`, the broker, and `.env` work.
- No logging, retries, backoff, reconnect logic, tests, types, CLI flags, extra config, or dependencies beyond distro `python3-paho-mqtt`. Never add `requirements.txt`.
- Publish-only is the default. Anything that acts on the host (runs `systemctl`, controls a process, anything an MQTT command triggers) needs an explicit opt-in `.env` setting that is off when unset or empty, and runs only on the command, never per sample. That setting is the one allowed extra config. Pattern: `LIGHTDM_SWITCH_MODE=control` (`WILDRIG_SWITCH_MODE=control` gates the WildRig mining switch, per-GPU enable switches and intensity sliders). XMRig mining predates this rule and has no opt-in yet.
- systemd: every systemd interaction goes through an interface in `lib/system_common.py`, never `systemctl`, `journalctl`, `loginctl`, cgroup paths, `/run/systemd`, or D-Bus in a collector. Service state/control and logs: `service_manager()` (`is_active(name)`, `start(name)`, `stop(name)`, `follow_log(name)`). Login sessions: `session_source()` (`active_users()`). systemd/logind are the only shipped backends. Another init system (OpenRC, runit, s6, …) is a new class with the same methods returned from that function: no collector change, no `.env` setting. We do not implement other backends (`CODE_OF_CONDUCT.md`, Pluggable service manager).
- Do not add systemd hardening, `[Unit]` keys, or healthchecks. Units do use `Restart=on-failure` and `RestartSec=10`.
- Do not drop root or add `User=`. If the work should not run as root, it is the wrong repo.
- Treat supply-chain risk as a reason to rewrite a sensor in stdlib rather than to import one more thing. Existing sensors need not be rewritten on sight.
- Do not persist energy, add `last_reset`, MQTT TLS, or HA extras unless asked.
- Do not introduce a Sensor class. Different sources get their own small scripts.
- Code reuse: each source gets its own small script and its own normal (non-template) systemd unit that can be enabled from the repo path. Do not generalize whole collectors (no template units, no per-instance settings). But when two scripts share logic that is plausibly useful elsewhere (reading unit state, a switch mode check, switch discovery/command handling), extract that part into `lib/` instead of copying it (see Shared code), as a building block something else can easily leverage later, not a merged collector (`CODE_OF_CONDUCT.md`, Keep AGENT.md small). Leave the rest of each script explicit.
- Leave existing comments and defensive parsing in the current scripts. Do not clean them up and do not copy them into new ones.

Hardware stats (monitor-only CoolerControl replacement) are allowed many sensors per process: `hwmon_sensors.py` and `windows/lhm_sensors.py` publish every input they find and sample every 5 s (not ~1 s); `nvidia_gpu_power.py` adds temperature, fan %, core/memory clock, utilization, memory utilization, power limit, pstate, throttle reasons (`clocks_event_reasons.active` bitmask string), PCIe link and throttle slowdown (`entity_category: diagnostic`), and a VRAM `near_full` attribute on memory used % (category unchanged) as `gpu_<uuid>_<Model>_<metric>` (card UUID and name from the same query, on the GPU's linked device) to its single `nvidia-smi --loop=1` when `NVIDIA_GPU_STATS` is non-empty (empty: power + energy only, unchanged); `[N/A]` / `[Not Supported]` fields get no entity. Every query field must be listed by `nvidia-smi --help-query-gpu` (one unknown name rejects the whole query; there is no PCIe replay field). No GPU hotspot on Linux.

## Shared code

- Generic code (settings, identity/slot ids, discovery builders, client + availability, rediscovery) lives in `lib/mqtt_common.py`. Code used only by one family of collectors lives in `lib/<family>_common.py` (`chia_common`, `nvidia_common`, `board_common`, `system_common`, `xmrig_common`); a new family gets its own module, never `mqtt_common`.
- Import as `from lib.mqtt_common import ...` / `from lib.<family>_common import ...`. Root scripts need nothing else (their directory is on `sys.path`). Scripts in a subdirectory (`support/`, `windows/`) first insert the repo root: `sys.path.insert(0, str(Path(__file__).resolve().parents[1]))`. `lib/` modules import each other the same way (`from lib.mqtt_common import ...`).

## Layout

- `lib/` — shared code only, no collectors (package, `lib/__init__.py`)
- `lib/mqtt_common.py` — dotenv, hostname, `get_machine_id()` (`MACHINE_ID` as written, validated, else hostname as-is), `machine_name()` (device display name), `id_part()` (case-kept slug) / `entity_id()` (lowercase `default_entity_id`), `id_slug()`, `slot_id()`, discovery (`default_entity_id` = `<platform>.<unique_id>`), client + LWT, `online` repeat after discovery, rediscovery (`_watch_discovery`: republish on a cleared config topic), switch helpers (discovery, `read_only|control` mode, command handling), `make_number_discovery`
- `lib/system_common.py` — `service_manager()` (service-manager interface; `SystemdServiceManager` is the only backend: cgroup read, `systemctl start|stop`, `journalctl -u … -f` log follow), `session_source()` (session interface; `LogindSessionSource` reads `/run/systemd/users`, also written by elogind)
- `lib/chia_common.py` — `chia_root()` (uid 1000)
- `lib/nvidia_common.py` — `clean_gpu_name()`, `short_model()`, `gpu_stat_id()` (card-keyed ids), `gpu_device()` (a GPU's linked device), `gpu_inventory()` (one nvidia-smi query: index, UUID, name, PCI bus), `gpu_entities()` (topics + discovery on the GPU's linked device, including stall sensors and VRAM `near_full`), `stall_fields()` / `publish_gpu_extras()`, `parse_line()` / `read_n()` (N rows per sample, no select()) / `no_data()` (exit message with nvidia-smi's rc and output), Linux and Windows `nvidia_gpu_power.py`
- `lib/board_common.py` — `dmi_board_id()` / `pick_board_id()` (board serial, else system UUID, else vendor + name), `hwmon_sensors.py` and `windows/lhm_sensors.py`
- `cpu_package_power.py` — RAPL package, fd held open, wrap via `(curr - prev) % max_energy_range_uj`
- `nvidia_gpu_power.py` — one plain query for the GPU count, then one `nvidia-smi --loop=1`, multi-GPU; the stream ending exits 1 (systemd `Restart=on-failure`); with `NVIDIA_GPU_STATS`, stall sensors (`entity_category: diagnostic`) and VRAM `near_full` too
- `interrupts_rate.py` — `/proc/interrupts` fd held open, 1 s rates (`entity_category: diagnostic`): total, max per CPU (`cpu` attribute), LOC/RES/CAL/TLB/IWI; top device IRQ sources as attributes on total; CPU hotplug and downward counters skipped for that interval
- `systemd/interrupts_rate.service` — `/root/mqtt-sensors`
- `psi_stall.py` — `/proc/pressure/{cpu,memory,io}` fds held open, 1 s (`entity_category: diagnostic`); state is `%` of the interval stalled from `total` microseconds (`some` for cpu/memory/io, `full` for memory/io), `avg10` as attributes; exits if PSI is absent
- `systemd/psi_stall.service` — `/root/mqtt-sensors`
- `collector_cost.py` — `/proc` scan, 1 s (`entity_category: diagnostic`); cmdline match of repo-root and `support/` collector scripts; total CPU % + voluntary/nonvoluntary context-switch rates, including itself; per-collector breakdown as attributes
- `systemd/collector_cost.service` — `/root/mqtt-sensors`
- `nvidia_xid.py` — `/dev/kmsg` held open (`entity_category: diagnostic`); `total_increasing` count of `NVRM: Xid` lines from the current boot, then new records; `last_xid` / `last_source` attributes; Linux only
- `systemd/nvidia_xid.service` — `/root/mqtt-sensors`
- `chia_farm_size.py` — held HTTPS to farmer `get_harvesters_summary` and full node `get_blockchain_state`; plots + TiB + effective TiB + netspace EiB + ETA seconds `(space/effective)*18.75`; certs under uid 1000 home
- `systemd/chia_farm_size.service` — `/root/mqtt-sensors`
- `chia_recompute_server_processing_time.py` — one `service_manager().follow_log("chia_recompute_server")` (systemd: `journalctl -u chia_recompute_server -f`), each line → full-precision seconds, display 1 decimal
- `systemd/chia_recompute_server_processing_time.service` — `/root/mqtt-sensors`
- `chia_harvester_processing_time.py` — held `debug.log` fd under uid 1000 home, eligible-plots lines → processing time (s) + plot count (`Total N plots` on the same line; allowed two-sensor exception), reopen on inode change
- `systemd/chia_harvester_processing_time.service` — `/root/mqtt-sensors`
- `loginctl_active_users.py` — `session_source().active_users()` (logind: `/run/systemd/users`), names with state `active`/`online`, comma-separated; do not spawn `loginctl`. sshfs: skip `pam_systemd` for group `sshfs` (README).
- `systemd/loginctl_active_users.service` — `/root/mqtt-sensors`
- `lightdm_active.py` — `service_manager().is_active("lightdm")` → MQTT switch ON/OFF; `LIGHTDM_SWITCH_MODE=control` starts/stops the unit
- `systemd/lightdm_active.service` — `/root/mqtt-sensors`
- `ollama_active.py` — `service_manager().is_active("ollama")` → MQTT switch ON/OFF; `OLLAMA_SWITCH_MODE=control` starts/stops the unit
- `systemd/ollama_active.service` — `/root/mqtt-sensors`
